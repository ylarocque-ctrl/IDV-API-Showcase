# IDV API Showcase — File Manager API Demo

A self-contained web app used by Quadient technical teams to demo the File Manager REST
API to customers. It builds every request visually — no one hand-types JSON or query
strings during a live demo. One HTML file, one config file, no backend, no build step.

## What it does

Tabs across the top switch between endpoints. Each tab is self-contained (own state,
own request builder, own curl generator, own "Send" handler) and shows the exact request
live before it's sent:

| Tab | Method + path | Builds |
|---|---|---|
| File Upload | `POST /v1/api/upload` | Multipart `file` + `jreq` JSON (see tested shape below) |
| Add/Modify Metadata | `POST /v1/api/file/add-metadata` | JSON body keyed by `TID`/`FID`/`TMPLID` + `Metadatas` |
| File Listing | `GET /v1/api/files/list` | Query string (`currentFldrID`, paging, dates, response fields) |
| Get Fields | `GET /v1/api/fields/{TMPLID}` | Request path from a template ID |
| File Download | `GET /v1/api/file/download/{FID}` | Request path from a file ID; the response **is** the PDF, previewed inline (see below) |
| Search (Basic) | `GET /v1/api/search` | Query string (keyword, owner, location, dates, type filters) |
| Search (Advanced) | `GET /v1/api/search` | Query string, shape changes with the chosen `searchType` (Files/Folders, Emails, Metadata) |

Shared UI, present on every tab:
- **Environment picker** (header) — switches base URL, from `config.json` → `environments`.
- **Tabs picker** (header) — show/hide endpoint tabs at runtime without editing files; which tabs load visible by default is set in `config.json` → `tabs`.
- **Config badge** (header) — reads **"config.json loaded"** when the file was fetched successfully, or **"built-in defaults (config.json not found)"** when it fell back to the constants baked into `index.html` (see `DEFAULT_CONFIG` in the file). Always check this badge before a demo.
- **API key field** — pre-filled from `config.json`, editable per-session without touching the file.
- **Send** — calls the API directly from the browser (needs CORS, see below).
- **curl (bash) / curl (Windows)** tabs — copy-as-curl fallback that always works, CORS or not.
- **Response panel** with a copy button.

## "Network error" and what it actually means

`fetch` rejects with a bare `Failed to fetch` whenever the browser refuses to hand the page a
response, and the browser deliberately gives JavaScript no way to learn why. Two very different
situations produce the identical error:

1. The request never left, or was rejected at the CORS preflight — **nothing happened on the
   server**.
2. The request *was* delivered and the server acted on it, but the response lacked
   `Access-Control-Allow-Origin`, so the browser dropped it — **the change is already applied**.

For a read-only GET the difference doesn't matter. For the two tabs that write — File Upload and
Add/Modify Metadata — it matters a great deal, because case 2 makes "just try again" a way to
apply the same change twice. Those two tabs therefore show an explicit warning that the request
may already have landed, rather than claiming it never reached the server.

### "Was it applied?" — the read-back on Add/Modify Metadata

When a metadata POST is blocked, the response panel grows a **Was it applied?** box. It answers
the question the browser refuses to: it re-reads the file through
`GET /v1/api/files/list` — a plain GET, unaffected by whatever blocked the POST — finds the record
for the FID that was just written to, and compares its timestamps against the moment Send was
pressed.

The folder is pre-selected from the File Upload tab's current folder (a preset sets it), falling
back to the File Listing tab's folder and then to the first entry in `config.folders`, so in the
normal demo flow it really is one click. Listing is folder-scoped and has no by-FID filter, which
is why the box asks rather than guesses silently.

Four outcomes, all of them deliberately cautious:

| Verdict | Meaning |
|---|---|
| Consistent with the write having been applied | The record's newest timestamp is at or after the send time. **Do not retry** without checking the values first. |
| Probably not applied | The newest timestamp predates the send. Retrying is probably safe. |
| File not in this folder | Nothing matched that FID there — pick the right folder. This is *not* evidence the write failed. |
| Couldn't check | The read-back itself failed (blocked, non-200, or a non-JSON body). Use **Copy read-back curl** and run it from a terminal. |

The response shape isn't hard-coded — the box walks the parsed JSON for any object carrying a
matching `FID`, so `allFiles`, `files`, a bare array or a nested envelope all work. A caveat is
always printed, because timestamps returned without an explicit timezone are read as the local
machine's time; treat a near-miss as inconclusive rather than proof.

File Upload gets the reworded warning but no read-back box: verifying a *new* file is a different
question from verifying a change to a known FID.

## The File Download response — a PDF, not JSON

`GET /v1/api/file/download/{FID}` streams the **PDF bytes back on the response itself**
(`Content-Type: application/pdf`). An earlier version of the API answered with a JSON
envelope carrying a time-limited `sasUrl` to blob storage instead.

The app does not hard-code either shape. It reads the response as an `ArrayBuffer` and
classifies it at send time:

- **PDF** — matched on `Content-Type: application/pdf` *or* on the `%PDF-` file signature in
  the first five bytes, so a deployment that mislabels the body as
  `application/octet-stream` is still handled. The bytes become a `blob:` URL, previewed
  inline in an `<object>` (the browser's own PDF viewer) with **Save** and **Open in new
  tab** buttons beside it.
- **JSON with `sasUrl`** — the legacy shape; pretty-printed with the original Download
  button, so older environments keep demoing correctly.
- **Anything else** — pretty-printed as JSON or plain text, exactly like the other tabs.

Above the body, the Response panel prints a short readout — Content-Type, the filename the
server suggested, body size, and which shape was detected. That is the fastest way to
confirm what an environment is actually returning without opening devtools.

Two things worth knowing:

- **Filenames need a CORS opt-in.** JavaScript can only read `Content-Disposition` on a
  cross-origin response if the API also sends
  `Access-Control-Expose-Headers: Content-Disposition`. Without it the download still works,
  it just falls back to `file-<FID>.pdf`. The readout says which case you're in.
- **Inline preview depends on the browser's PDF viewer.** Some hardened/managed Chrome and
  Edge profiles disable it; the preview then shows a short fallback message and Save / Open
  in new tab still work. Embedding a viewer would mean shipping pdf.js, which would break the
  no-dependencies rule.

The per-row **Download** buttons in File Listing and both Search tabs call this same endpoint
and use the same detection, so the two can't drift apart.

The generated curl for this tab uses `--output` (write the PDF to a file rather than dump
binary into the terminal) and `-D -` (print the response headers so the content type is
visible at a glance).

## The tested File Upload payload — do not regress

`POST /v1/api/upload` as multipart/form-data with a `file` part and a `jreq` part. `jreq`
is assembled from the form and must keep this exact shape:

```json
{
  "currentFldrID": <number>,
  "metadata": [
    {
      "TMPLID": <number>,
      "Fields": [ {"Name": "...", "Value": "..."} ],
      "Groups": [ {"Name": "...", "Fields": [ {"Name": "...", "Value": "..."} ]} ]
    }
  ]
}
```

Any change to the request-building logic must be verified against this shape byte-for-byte
before it's considered done.

## Run it

> **Don't just double-click `index.html`.** A `file://` address blocks `fetch()` of local
> files, so the app can't read `config.json` and silently falls back to built-in defaults —
> your edits to environments, API key, folders, templates, and presets won't appear. Serve
> the folder over HTTP instead. Confirm it worked via the config badge in the header.

1. **Open a terminal in this folder.** Windows: click the address bar in File Explorer,
   type `cmd`, press Enter.
2. **Start a local server:**

   ```
   python -m http.server 8000
   ```

   No Python? Try `py -m http.server 8000`, use VS Code's "Live Server" extension, or run
   `npx serve` with Node.js installed.
3. **Open** http://localhost:8000 and check the config badge.

Any static host works for sharing with the team: Azure Static Web Apps, an Azure Storage
static website, IIS, nginx, etc.

### Run it automatically (Windows service, optional)

If you're tired of opening a terminal every time, `windows-service/` has scripts that
register `python -m http.server` as a real Windows service using
[NSSM](https://nssm.cc/download) (Non-Sucking Service Manager) — a small, widely-used
utility for wrapping any command-line program as a service. Once installed, the demo
server starts at boot and restarts itself if it ever crashes.

**Setup (one-time):**

1. Download NSSM from https://nssm.cc/download and copy `nssm.exe` (from the `win64`
   folder in the zip) into `windows-service/`.
2. Right-click `windows-service/install-service.ps1` → **Run with PowerShell** (or run it
   from an elevated terminal). It will prompt for admin rights (UAC) if needed.
3. It finds Python automatically, registers the service, starts it, and prints its
   status. Open http://localhost:8000 and check the config badge as usual.

**Day to day:**

| Script | Does |
|---|---|
| `install-service.ps1` | Installs/reinstalls the service. Optional params: `-Port 8000 -ServiceName IDVApiShowcase`. |
| `status-service.ps1` | Quick check — installed? running? (no admin needed) |
| `uninstall-service.ps1` | Stops and removes the service. |

Manage it anytime via `services.msc` (name: **IDV API Showcase - Demo Server**), or the
`nssm status IDVApiShowcase` / `Start-Service` / `Stop-Service` cmdlets. Logs land in
`logs/service-out.log` and `logs/service-err.log` in the project root.

**Trade-off to know:** NSSM is a third-party portable executable, not a Windows built-in.
If your machine's endpoint security blocks running unrecognized `.exe` files, ask IT for
an exception or fall back to a Task Scheduler "run at startup" task instead (no
third-party download, but not a real restartable service). This doesn't change anything
about the app itself — same `index.html`/`config.json`, same CORS and API-key
considerations as running it manually.

## Customize — edit config.json

| Key | Controls |
|---|---|
| `appTitle` / `appSubtitle` | Header branding |
| `environments` | Base URLs in the header dropdown (add sandbox/prod here) |
| `apiKey` | Pre-filled Authorization header (editable in the UI at demo time) |
| `tabs` | Which endpoint tabs are visible on load; `endpoint` must match a tab's `data-endpoint` in `index.html` |
| `uploadEndpoint` | Method, path, multipart field names (`file`, `jreq`), and `defaults.currentFldrID` — the folder pre-selected on load. Must match an `id` in `folders`, or the first folder wins |
| `metadataEndpoint` | Method, path, defaults for `TID`/`FID`/`TMPLID`. `FID` ships empty so nothing is pre-filled |
| `listEndpoint` | Method, path, paging defaults, tickable `responseFields` |
| `fieldsEndpoint` | Method, path, default `TMPLID` (ships as `2`, Claim) |
| `downloadEndpoint` | Method, path, default `FID` (ships empty). The response shape is detected at runtime, not configured — see `_downloadResponseNote` in `config.json` |
| `searchEndpoint` | Method, path, defaults, owner/location/date/type option lists |
| `advancedSearchEndpoint` | Method, path, defaults, `searchType` + field-type option lists |
| `folders` | Friendly entries for the destination-folder dropdown (shared across tabs) |
| `templates` | Known TMPLIDs with `availableFields` / `availableGroups` — drives field/group names and autocomplete in the metadata builder. `FLDID`/`GRPID` also make a template's fields usable in Search (Advanced) → Metadata |
| `presets` | One-click demo scenarios that pre-fill a tab's metadata values. **Presets do not change the destination folder** — that stays wherever the demoer set it. The `currentFldrID` still present on each preset is no longer read; set the starting folder in `uploadEndpoint.defaults.currentFldrID` instead |

After editing, refresh the page. JSON must stay strictly valid (no comments, no trailing
commas) — a syntax error is the most common reason the badge shows "built-in defaults."

Field/template notes (also documented inline in `config.json` under `_fieldTypeLegend` and
`_searchFieldNote`):
- `Type`: `1` = Text, `2` = Numerical, `3` = Date (set `DateFormat`), `4` = Dropdown (set
  `Options`). Optional `Mandatory: true` requires a value before sending. For `Type: 4`,
  optional `Multiple: true` allows selecting several options (sent as a comma-separated
  Value).
- Template `Fields`/`Groups` use `Name`; presets additionally carry `Value` (only
  `Name`/`Value` enter the `jreq`/`Metadatas` payload).
- Search (Advanced) → Metadata reuses the same `templates`. To make a field searchable, add
  the backend `FLDID` to it (and `GRPID` to its group). Fields without `FLDID` still
  render, with an editable ID box so a demoer can type the real ID at runtime.

## Adding a new endpoint tab

`index.html` has an inline comment marking the extension point (search for "To add an
endpoint later"): add a `<button data-endpoint="...">` in the nav, then a matching
`<div class="endpoint-panel" data-endpoint="...">` in `<main>`. Each existing tab is a
self-contained block (state, builder, curl generator, send handler) you can copy as a
starting pattern. New endpoint definitions belong in `config.json`, not hard-coded in the
app.

## Version number

Shown in the header, set by the `APP_VERSION` constant near the top of the `<script>` in
`index.html`. Update it there and refresh.

## Security note

`config.json` ships the demo API key in plain text to anyone who can load the page. Keep
this app on an internal host or behind authentication — never publish it to the open web,
and never put a real key into examples or documentation.

## CORS

"Send" calls the API directly from the browser, so the API must allow the app's origin via
CORS. If a request works in curl but fails here with a network error, that's almost always
CORS — host the app on the same domain as the API, allow the demo origin on the API, or use
the built-in curl tabs as a fallback.
